02ขนาดของสิ่งที่ส่ง ต้องสมกับสิ่งที่เขาขอ

ถ้าเขาขอ script ให้ส่ง script ถ้าคิดว่าควรเป็น package ให้เสนอเป็นทางเลือกพร้อมเหตุผล อย่าตัดสินใจแทนแล้วส่งของใหญ่กว่าที่ขอ

ทำไม: โครงสร้างที่ใหญ่เกินงานไม่ได้ฟรี — คนที่มารับช่วงต้องเปิด 9 ไฟล์เพื่ออ่าน flow เดียว และทุกไฟล์กลายเป็นของที่ต้อง maintain ตลอดอายุโปรเจกต์ ข้อนี้เคยเป็นจุดอ่อนของมาตรฐานชุดนี้เอง และแก้แล้วในรอบที่สอง — ดูตัวเลขหลังแก้ข้างล่าง

03Abstraction ต้องมีผู้ใช้จริงอย่างน้อย 2 ราย

interface, abstract class, factory, DI container — สร้างได้เมื่อมีผู้ใช้จริงตอนนี้ตั้งแต่ 2 รายขึ้นไป หรือมี requirement ชัดว่ากำลังจะมี ถ้าอธิบายไม่ได้ว่ามันกันความเจ็บปวดอะไร แปลว่ายังไม่ถึงเวลา

ทำไม: เพิ่ม abstraction ทีหลังทำได้เสมอ แต่รื้อ abstraction ที่ผิดออกต้องแตะทุกจุดที่มันแทรกอยู่ — over-engineering แพงกว่า under-engineering เพราะมันแก้ยากกว่า และ test ที่ใช้ object literal แทน implementation จริงไม่นับเป็นผู้ใช้รายที่สอง

07ห้ามกลืน error และห้ามตอบ 200 ทุกกรณี

ทุก catch ต้องเลือกอย่างใดอย่างหนึ่ง: จัดการให้จบจริง, log พร้อม context แล้วโยนต่อ, หรือแปลงเป็น error ที่มีความหมายกว่าเดิม และ status code ต้องสื่อความจริง

ทำไม: catch (e) {} ทำให้ปัญหาหายไปจากสายตาทุกคน ส่วนการตอบ 200 {ok:false} ทำให้ client, monitoring, load balancer และ retry logic ทั้งหมดเข้าใจว่าสำเร็จ — กราฟ error rate จะเป็นศูนย์ตลอดขณะที่ระบบพังอยู่

09Idempotency ต้องบังคับที่ database ไม่ใช่ในหน่วยความจำ

งานที่ห้ามทำซ้ำ (ตัดเงิน, สร้างออเดอร์, ส่งอีเมลยืนยัน) ต้องกันซ้ำด้วย unique constraint หรือ transaction ไม่ใช่ check-then-write ในโปรเซส

ทำไม: payment gateway ทุกเจ้าส่ง webhook ซ้ำเป็นเรื่องปกติ (retry เมื่อ timeout) และเรารันหลาย instance การเช็คใน memory ถูกต้องเฉพาะตอนมีเครื่องเดียวและไม่เคย restart ซึ่งไม่ใช่ production

export class InMemoryProcessedEventStore {
  private readonly seen = new Set<string>();

  async claim(eventId: string): Promise<boolean> {
    if (this.seen.has(eventId)) return false;
    this.seen.add(eventId);      // check-then-write
    return true;

✓Checklist ก่อนเปิด PR

อ่านโค้ดที่เพิ่งเขียนอีกรอบในมุมคนที่ต้องมา maintain ต่ออีกหกเดือน เจออะไรแก้เลย ไม่ต้องรอให้คนรีวิวทัก

ความถูกต้อง

  • ไม่มี TODO, stub, mock ที่ต่อเข้าเส้นทางจริง
  • ไม่มี console.log / print / debugger ค้าง
  • ไม่มี dead code หรือ import ที่ไม่ได้ใช้
  • async: await ครบทุกที่ที่ต้องรอ
  • ถ้าเป็น refactor — พฤติกรรมเดิมยังเหมือนเดิมทุกเงื่อนไข

Edge case

  • empty, null / undefined / None
  • ค่าติดลบ, ศูนย์, ค่าตรงขอบพอดี (off-by-one)
  • list ยาว → มี pagination หรือ streaming
  • unicode / อักษรไทย / emoji
  • timezone: เก็บ UTC แปลงตอนแสดงผล
  • กดซ้ำ / ส่งซ้ำ → idempotent

Security

  • ไม่มี secret hardcode (grep: password, api_key, token)
  • input จากภายนอก validate ด้วย schema
  • query parameterized ทั้งหมด
  • เช็คสิทธิ์ระดับ resource ไม่ใช่แค่ว่า login แล้ว
  • log ไม่มี password / token / PII

Performance

  • ไม่มี N+1 query
  • ไม่มี await ในลูปที่รันขนานได้
  • ไม่โหลดทั้งตารางมา filter ในโค้ด
  • connection / file handle / listener ถูกปิด

ความอ่านง่าย

  • type ครบ ไม่มี any
  • ชื่อบอกเจตนาโดยไม่ต้องเปิด implementation
  • ไม่มี magic number ลอย ๆ
  • ตามสไตล์ของ repo ไม่ใช่สไตล์ตัวเอง
  • abstraction ทุกตัวมีผู้ใช้จริง ≥ 2 ราย

ส่งมอบ

  • รัน test จริงแล้ว — ถ้าแดง บอกพร้อม output
  • ถ้ารันไม่ได้ บอกว่ารันไม่ได้ ไม่ใช่รายงานตัวเลข
  • บอก env var / migration ที่ต้องตั้งเพิ่ม
  • บอกสิ่งที่สมมติไว้และสิ่งที่ยังไม่ได้ทำ
  • commit message บอกผลลัพธ์ ไม่ใช่บอกว่าแก้ไฟล์ไหน
